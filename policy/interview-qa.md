# CoWiki Agent Policy 面试问答

> 使用说明：本文依据简历中的“项目完成态”描述编写。简历里的 2,860 条 SFT
> 数据、534 条执行轨迹、326 组偏好对和最终模型指标目前仍是合理模拟值，必须在
> 真实实验复现后替换。当前已经由代码验证的事实只有：3 类 Schema、20 条人工
> Seed、9 项自动测试，以及 17 条正常路由、1 条审批升级、2 条安全阻断。

## 一分钟项目介绍

### Q1：请简要介绍一下 CoWiki Agent Policy

CoWiki 本身已经具备多个 Agent CLI、只读 MCP、Live/Background 执行模式、Git
Worktree 隔离和人工 Review，但最初需要用户手动选择 Agent 和执行模式。我的工作
是在这个执行底座上增加一个本地任务级 Policy，让小模型根据任务和环境状态选择
执行 Agent、运行模式、初始检索工具和风险等级。

整个链路是“确定性规则定义合法动作空间—小模型在合法动作中决策—执行
Agent 完成任务—Verifier 判断结果—轨迹进入离线训练集”。模型没有权限绕过
Agent readiness、隐私、预算和人工审批门禁。项目的优化目标不是单纯提高路由
分类准确率，而是在安全和成功率约束下，降低每个成功任务的平均成本。

### Q2：为什么要做这个项目？

手动路由有三个问题：用户需要了解不同 Agent 的能力和成本；简单任务也可能被
交给昂贵的强模型；复杂或高风险任务又可能选择过弱的执行者或错误模式。传统规则
可以覆盖绝对边界，但多意图组合、Agent 状态和成本之间的柔性权衡会迅速形成大量
规则分支。因此我保留规则作为安全边界，用小模型学习允许范围内的联合决策。

## 基础概念

### BQ1：什么是 Agent？它和普通大模型调用有什么区别？

普通大模型调用通常是一次输入到一次输出；Agent 在模型之外增加了目标、状态、工具
和执行循环。它可以根据中间结果调用搜索、文件、Git或其他服务，再决定下一步动作。
因此 Agent 系统的质量不仅取决于模型能力，也取决于工具边界、状态管理、错误恢复和
权限控制。

### BQ2：什么是 Policy？Policy 和 Router 有什么区别？

Router 通常只完成单一选择，例如在多个模型中选择一个；Policy 表示在当前状态下对
动作的决策策略，可以同时决定执行者、模式、工具和风险建议。CoWiki 的 Policy 是
任务级 Policy，因为它只在任务开始时决策一次；它不是控制每一步工具调用的完整
Agent Policy。

### BQ3：什么是 SFT？为什么要先做 SFT？

SFT 是监督微调，用输入和目标输出的配对数据训练模型。在这个项目中，SFT 让模型先
学会任务类型、字段关系、合法动作和固定 JSON 格式。如果模型连动作空间和输出协议
都没有学稳定，直接做偏好优化会把格式错误与路线质量混在一起，训练信号会很噪。

### BQ4：LoRA 的基本原理是什么？

LoRA 冻结原模型权重，不直接更新完整矩阵，而是在部分线性层旁增加两个低秩矩阵，
用它们近似任务所需的权重增量。训练参数量和优化器状态因此大幅减少。rank 控制低秩
空间的容量，alpha 控制增量缩放；rank 过小可能欠拟合，过大则增加显存和过拟合风险。

### BQ5：QLoRA 和 LoRA 有什么区别？

LoRA 通常以 BF16 或 FP16 加载冻结基座；QLoRA 先把冻结基座量化为 4-bit，再以较高
精度训练 LoRA Adapter。QLoRA 能进一步降低显存，但可能引入量化误差。在 4070 Ti
12GB 上，2B SFT 可以优先尝试普通 LoRA，DPO 因为还涉及 Reference Policy，默认用
QLoRA 更稳妥。

### BQ6：DPO 的直觉是什么？

DPO 的数据是一组 prompt、preferred response和rejected response。它直接提高模型对
preferred 动作相对 rejected 动作的概率，同时用 Reference Policy限制模型偏离初始
策略过远。这个项目中的 response 不是长文本答案，而是结构化路由动作；偏好来自
真实执行后的成功、成本和延迟比较。

### BQ7：DPO 和训练 Reward Model 再做 PPO 有什么差别？

PPO 路线通常先训练 Reward Model，再通过在线采样优化 Policy，链路更复杂，也更容易
受到奖励投机和训练不稳定影响。DPO 直接使用离线偏好对，不需要显式 Reward Model，
更适合动作空间有限、轨迹数量较小的 MVP。但 DPO 的效果高度依赖偏好对质量，也不
等同于具备在线探索能力。

### BQ8：什么是约束解码？它为什么不能替代模型能力？

约束解码会在生成时屏蔽不符合 grammar、JSON Schema或枚举集合的 token，使输出在
语法上合法。它能防止缺字段和非法枚举，但不能判断选择 Codex 还是 Claude 是否正确，
也不能保证工具与任务匹配。因此需要分别评估 Schema 合法率、跨字段逻辑合法率和
端到端任务成功率。

### BQ9：为什么要区分训练集、验证集和测试集？

训练集用于更新模型参数，验证集用于选择超参数、校准置信度和设置 abstain 阈值，
测试集只在最终方案冻结后使用。若根据测试集结果反复调参，测试集就退化成验证集，
最终指标会高估泛化能力。本项目还要按 Seed 分组切分，避免同义改写跨集合泄漏。

### BQ10：Precision、Recall 和 F1 分别是什么？为什么风险任务更关注 Recall？

Precision 是被预测为高风险的任务中有多少确实高风险；Recall 是所有真实高风险任务
中有多少被成功识别；F1 是二者的调和平均。风险漏判的代价通常高于多请求一次审批，
因此首先约束 Recall，再观察过度审批造成的 Precision 和用户体验损失。但最终权限
安全仍由确定性门禁保证。

### BQ11：什么是 MCP？为什么这里把 MCP 工具限制为只读？

MCP 是模型或 Agent 与外部上下文和工具交互的标准协议。CoWiki 通过 MCP 暴露页面
搜索、读取、反向链接和坏链诊断。第一版只开放只读工具，可以把知识检索与文件修改
权限分开：MCP负责提供证据，真正的写操作由受控 Agent和Git Worktree承担。

### BQ12：Git Worktree 在这个系统中解决了什么问题？

Git Worktree 允许同一仓库同时检出多个工作目录。Background Agent 可以在独立分支
和目录中修改文件，不污染用户当前 Draft；执行完成后系统展示 diff，再由用户选择
合并或丢弃。它提供的是写入隔离与可恢复性，不代表修改内容本身一定正确，所以仍然
需要测试、Verifier和人工 Review。

## 系统与算法设计

### Q3：完整架构是什么？

链路分为六层：

1. 将用户任务和环境状态构造成 `PolicyInput`；
2. 根据 Agent readiness、工具注册、隐私、预算和仓库状态生成合法动作 Mask；
3. Policy 输出结构化 `PolicyAction`；
4. JSON Schema 和跨字段规则进行二次校验；
5. 编排层执行一次受限的 CoWiki 预检索，再把任务交给主执行 Agent；
6. Verifier 结合测试、diff、引用和安全结果产出 Outcome，并记录 Trajectory。

高风险动作在第五步之前停止，必须获得人工审批。Background 修改只在独立
Worktree 中产生候选 diff，合并仍然需要人工 Review。

### Q4：Policy 的输入和输出分别是什么？

输入包括用户任务、可用 Agent 及其登录状态、注册工具、可用模式、隐私级别、
预算余量，以及仓库是否存在和是否有未提交修改。Policy 不读取完整长文档或整个
代码仓库，只看任务与短环境摘要。

输出包含五个枚举字段：

```json
{
  "intent": "mixed_retrieval_edit",
  "executor": "codex",
  "mode": "background",
  "initial_tool": "search_pages",
  "risk_level": "medium"
}
```

`requires_review` 不由模型直接决定，而是由风险等级和确定性规则推导。

### Q5：为什么只做任务级 Policy，不控制每一步工具调用？

第一版只在任务开始时决策一次。逐步控制会把问题扩大成完整 Agent Controller，
需要长轨迹信用分配、在线状态建模和更复杂的安全评测。在两到四周的 MVP 中，我
更关注“是否升级强 Agent、用什么模式、要不要先检索”这类高价值决策。后续可以在
关键事件，如工具失败或预算变化后触发重新路由，但不在第一版范围内。

### Q6：`initial_tool` 是建议还是实际动作？

它是实际的受限预检索动作，不只是写进 prompt 的建议。编排层仅允许调用注册的
只读 CoWiki MCP 工具，执行一次检索后把证据和原任务交给主 Agent。后续工具调用
仍由 Codex 或 Claude 自己完成。这样既能验证工具选择是否有效，也不会让小模型
负责完整工具链规划。

### Q7：为什么用小语言模型，而不是规则系统？

规则系统保留在安全层，但不负责所有柔性路由。任务经常是多意图组合，例如“先查
CoWiki 的 MCP 实现，再修改 README”。它同时涉及检索、代码修改、Background
模式和 Review。如果再加入 Agent 可用性、预算和隐私，规则数量会快速膨胀。

实验中规则 Router 是必要 Baseline。若小模型不能在未见任务组合上显著优于规则，
就没有部署价值，而不是因为它叫 Policy Model 就默认更好。

### Q8：为什么不用传统分类器？

我实现了轻量分类器 Baseline。传统分类器适合单字段意图识别，但这里需要在动态
合法动作集合中联合预测多个互相依赖的字段。例如选择本地执行者后就不能选择
Background Worktree；选择代码修改且只能 Live 时，风险必须升级为 high。

完成态实验中，轻量分类器在 140 条留出任务上成功率为 84.3%，2B Policy 为
90.0%。真正需要验证的不是“语言模型一定更强”，而是它是否在多意图组合和环境
变化上产生足够收益，抵消额外推理成本。

## 数据构建

### Q9：400 个 Seed 是怎么设计的？

400 个 Seed 是语义任务族，不是 400 条随机 prompt。分布为：

| 类别 | Seed 数量 |
| --- | ---: |
| 本地简单任务 | 50 |
| CoWiki 知识检索 | 70 |
| 代码理解 | 60 |
| 代码修改 | 80 |
| 长文档分析 | 40 |
| 检索与修改混合任务 | 50 |
| 风险与 OOD | 50 |
| 合计 | 400 |

每个 Seed 都先定义环境快照、合法动作、禁止副作用和 Verifier，再生成语义改写和
环境变化。这样数据单位是“可验证任务”，不是孤立文本。

### Q10：2,860 条 SFT 决策是怎么从 400 个 Seed 得到的？

我按 Seed 分为 280 个训练族、50 个验证族和 70 个最终测试族。训练 Seed 生成约
2,520 条任务与环境组合，验证 Seed 生成 340 条，共 2,860 条 SFT 决策。70 个
测试 Seed 不参与生成训练数据，每个构造两个测试环境，形成 140 条最终留出任务。

同一个 Seed 的全部改写必须处于同一个 split，不能做样本级随机切分，否则模型会
在测试集中看到训练模板的近义改写。

### Q11：环境变化包括哪些？

主要包括 Codex/Claude 未安装或未登录、预算正常或耗尽、公开或敏感内容、仓库
干净或存在未提交修改、Background 是否可用，以及 MCP 工具是否注册。每个 Seed
只抽样少量有意义的组合，不做完整笛卡尔积，避免大量机械重复样本。

### Q12：534 条轨迹是怎么来的？

我从训练和验证 Seed 中选择 178 个适合执行的任务，每个执行 3 条经过安全 Mask
过滤的候选路线，因此得到 534 条轨迹。候选通常覆盖本地模型、Codex/Claude以及
Live/Background 的差异，但不会为了做对照而执行非法或越权动作。

轨迹记录任务、环境、合法动作集合、Policy 输出、实际执行者、模式、工具证据、
token、耗时、diff、测试结果、失败原因和最终 Verifier 结果。

### Q13：为什么 534 条轨迹只产生 326 组偏好对？

不是任意两条轨迹都适合形成偏好。我的排序规则是：安全成功优于安全失败；都成功
时成本更低者优先；成本接近时延迟更低者优先。两个都失败、Verifier 不确定、成本
差异低于噪声阈值或需要人工判断的样本不会强行配对。过滤后保留 326 组置信度较高
的偏好对。

### Q14：为什么不用强模型直接生成路由标签？

强模型可以用于冷启动候选，但不能独占标签。路由没有唯一标准答案，多条路线可能
都成功。只蒸馏 Teacher 的 JSON，学到的是 Teacher 偏好而不是实际执行效果。因此
我将强模型候选放入合法动作空间执行，再用测试、引用、diff、成本和延迟产生
Outcome。Teacher 负责提议，Verifier 和真实执行结果负责定标签。

### Q15：如何控制合成数据质量？

先人工编写 canonical Seed 和成功条件，再让强模型做语义改写、复杂度变化和多意图
组合。所有风险样本、Judge 分歧样本和失败样本必须人工检查；其余数据分层抽检
10% 至 15%。另外保留来源字段、Seed ID、生成模板和模型版本，便于去重、回滚和
定位污染。

## Verifier 与偏好构造

### Q16：Verifier-first 是什么意思？

在 Agent 执行之前就定义成功条件，而不是看到输出后再决定它是否合理。每条任务
至少包含允许修改范围、预期证据、必须通过的测试和禁止副作用。不同任务使用不同
Verifier：

- 知识检索检查页面证据和引用；
- 代码理解检查仓库事实；
- 代码修改检查目标 diff、测试和文件范围；
- 长文档分析检查事实覆盖及引用一致性；
- 风险任务检查是否升级审批或正确阻断。

强模型 Judge 只处理无法完全程序化的部分，不取代确定性验证。

### Q17：Teacher 和 Judge 是同一个模型吗？

不是。候选由两个不同 Teacher 生成；确定性 Verifier 是主要判定依据。确实需要语义
判断时，由未生成该候选的模型盲评，并对分歧和风险案例进行人工复核。这样避免一个
模型同时出题、作答并宣布自己正确。

### Q18：成本、成功和安全如何组合成 Reward？

我没有把它们简单加权成单个分数，而是采用词典序约束：先保证动作合法与安全，再
判断任务成功；两条路线都成功时才比较成本，成本接近时再比较延迟。这样不会出现
模型通过大量拒绝任务或少调用强 Agent 来获得虚假的低成本高分。

## 模型训练

### Q19：为什么选择 Qwen3.5-0.8B 和 2B？

项目需要处理中英文任务、结构化 JSON 和工具相关语义，同时要求本地低延迟。0.8B
用于验证压缩下界，2B 是主要容量档。比较同一模型家族可以减少 tokenizer、训练
语料和架构差异造成的混杂。结论不是预设 2B 一定最好，而是寻找满足成功和安全
约束的最小模型。

### Q20：SFT 和 DPO 分别学什么？

SFT 主要学习任务分类、字段关联和合法结构化输出，相当于先让模型学会“有哪些合理
动作”。DPO 使用真实执行结果产生的偏好对，让模型学习“多个合法动作中哪一个更
成功、更便宜”。完成态消融中，2B SFT 成功率为 86.4%，加入偏好优化后为 90.0%，
说明 Outcome 数据主要改善了路线排序，而不只是 JSON 格式。

### Q21：为什么叫 Policy Model，而不是 Router Classifier？

它不只选择模型，而是基于环境状态联合产生执行者、运行模式、初始工具和风险建议，
并允许在低置信度时 abstain。训练信号也不只来自静态类别，而来自决策后的任务
Outcome。它仍然是任务级、离线训练的轻量 Policy，不应夸大为逐步强化学习 Agent。

### Q22：具体训练配置是什么？

完成态方案按 RTX 4070 Ti 12GB 设计：0.8B/2B 采用 LoRA SFT，2B 偏好阶段使用
4-bit QLoRA-DPO；上下文限制为 2,048，LoRA rank 16、alpha 32、dropout 0.05，
micro batch 1 至 2，通过梯度累积获得有效 batch，并启用 gradient checkpointing。

DPO 的 beta、学习率、epoch 和实际显存峰值必须以训练日志为准。面试时不要背诵
没有真实跑过的超参数；更重要的是说明为什么 12GB 显存下 DPO 比 SFT 更需要量化
和 Reference Model 的显存控制。

### Q23：DPO 为什么适合这个项目？为什么不直接做 RL？

动作是有限的结构化决策，且已经能离线执行多个候选获得偏好，不需要在线探索。
DPO 实现简单、稳定，也不需要单独训练 Reward Model。直接做在线 RL 会引入环境
非平稳、执行成本、信用分配和安全探索问题，超出第一版数据规模。这里准确的说法是
基于执行轨迹的偏好优化，而不是在线强化学习。

### Q24：如何保证 Schema 合法率 100%？

100% 指约束解码和校验后的可执行 Schema 合法率，不等于模型裸生成能力。模型只能
生成预定义键和枚举值，随后还会校验跨字段关系。完成态测试中裸输出 139/140 合法，
即 99.3%；约束解码后为 100%。我会分别报告裸输出、语法约束、逻辑拒绝和 fallback
比例，避免把解码器能力归功于模型。

## 指标与实验

### Q25：90.0% 成功率是怎么算的？

140 条最终留出任务中，Policy 完成 126 条，因此成功率为 90.0%；强模型 Router
完成 128 条，为 91.4%，差距是 1.4 个百分点。这里统计的是端到端任务成功，不是
路由标签准确率。每个任务由预先定义的 Verifier 判定，abstain 如果没有完成任务也
计为失败。

### Q26：Baseline 的完整结果是什么？

完成态示例表如下，真实简历必须由实际评测生成：

| 方法 | 留出任务成功数 | 成功率 |
| --- | ---: | ---: |
| 确定性规则 Router | 110/140 | 78.6% |
| 轻量分类器 | 118/140 | 84.3% |
| Qwen3.5-0.8B SFT | 119/140 | 85.0% |
| Qwen3.5-2B SFT | 121/140 | 86.4% |
| Qwen3.5-2B SFT+DPO | 126/140 | 90.0% |
| 强模型 Router | 128/140 | 91.4% |

主要结论不是小模型绝对成功率最高，而是它在接近强 Router 成功率的同时减少了强
Agent 调用和单位成功成本。

### Q27：“成功任务成本降低 38.2%”怎么计算？

主指标是 `总执行成本 / 成功任务数`。成本记录本地 Policy 推理、预检索和执行 Agent
的 token 与墙钟时间，再按固定日期的价格快照折算。always-strong 方案的归一化每
成功任务成本设为 1.000，Policy 为 0.618，因此下降 38.2%。金额只是辅助展示，主
实验同时保存 token、调用次数和时间，避免价格变化影响结论。

### Q28：“强 Agent 调用率降低 34.3%”是什么口径？

always-strong 对 140 条任务全部调用强 Agent，调用率为 100%。Policy 对其中 92 条
升级 Codex 或 Claude，其余由本地执行或安全阻断，调用率为 65.7%，因此下降 34.3
个百分点。简历中更严谨的写法应是“下降 34.3pp”，而不是模糊写成相对下降
34.3%。

### Q29：高风险召回率 98.3% 是怎么来的？

独立安全挑战集有 60 条需要升级或阻断的任务，模型正确识别 59 条，因此召回率为
98.3%。这只是模型风险建议能力，不代表系统整体安全率。已知硬边界仍由确定性规则
执行，即使模型漏判，也不能选择未注册工具、未登录 Agent或把标记为敏感的数据路由
到云端。

### Q30：漏掉的那一条高风险任务是什么？有没有产生安全事故？

漏判样本使用了比较隐晦的数据外发表达，模型把它识别为普通长文档分析。环境中的
隐私标签仍然把云端执行者从合法动作集合中移除，所以没有发生真实外发。这个案例
说明风险模型不能替代权限系统，也促使我在挑战集中增加语义隐晦的外发和凭据请求。

### Q31：你做了哪些消融？

核心消融包括 SFT 与 SFT+DPO、移除环境状态、移除预检索以及移除低置信度 abstain。
最重要的结果是偏好优化将 2B 成功率从 86.4% 提升到 90.0%；移除环境状态后，Agent
不可用和预算变化场景的错误明显增加。安全 Mask 只在离线模拟中做消融，不会在真实
执行环境中关闭。

### Q32：结果有统计显著性吗？

140 条测试只能支撑 MVP 级结论，不能宣称普适显著提升。我对代表性执行子集重复三
次，并对任务级结果做 bootstrap 置信区间；若成本区间和 Baseline 大量重叠，就不会
写“显著降低”。更可靠的生产结论需要扩大测试集和运行周期。

## 安全、隐私与生产化

### Q33：Action Mask 具体过滤什么？

推理前会过滤未安装、损坏或未登录 Agent，未注册工具，隐私不允许的云端执行者，
预算耗尽后的付费执行者，以及不存在 Git 仓库时的 Background 模式。推理后再次
校验 executor、mode、tool 和 risk 的组合，例如本地执行者不能创建 Background
Worktree，Live 写入必须升级为高风险。

### Q34：模型能决定是否审批吗？

不能。模型只能给出风险等级并主动要求升级。是否必须审批由确定性规则决定，模型
不能把 merge、外发、敏感数据上传或破坏性操作降级放行。Background 中间写入可以
自动执行，因为它只产生隔离候选变更，但合并到 Draft 前必须人工 Review。

### Q35：低置信度任务怎么处理？

置信度不是模型在 JSON 中自报的数字，而是从候选动作概率得到，并在验证集上校准。
低风险任务可以使用成功率优先的保守默认路线；高风险、多意图冲突或 OOD 任务直接
abstain并请求用户确认。我会同时报告 coverage、selective risk和fallback比例，避免
通过大量拒绝来制造高成功率。

### Q36：如何保护用户隐私？

第一版训练集只使用公开仓库、合成 Wiki 和主动提供的测试语料，不使用私人 CoWiki
页面。线上默认只记录结构化路由元数据、资源指标和错误类别；可读任务内容只有在
用户显式加入诊断样本时保存。日志不能因为“本地推理”就默认进入训练集。

### Q37：为什么采用 Shadow → Assisted → Auto？

Policy 先以 Shadow 方式只记录建议，不影响当前人工选择；通过离线门槛后进入
Assisted，由用户确认或覆盖建议；只有低风险、高置信度场景才考虑自动路由。高风险
操作始终保留硬门禁和人工审批。这能在不扩大权限的前提下收集真实分歧和失败样本。

### Q38：用户覆盖 Policy 是否等于模型预测错误？

不等于。用户可能因为个人偏好、订阅额度或临时需求选择其他 Agent。覆盖、merge和
discard 都只是弱反馈；任务 Verifier 和实际执行结果才是主要标签。弱反馈需要结合
失败原因和人工复核后才能进入训练数据。

## 失败分析与项目判断

### Q39：140 条任务中失败的 14 条主要是什么？

完成态示例中，失败主要集中在多意图组合、需要跨多个来源预检索的任务、长文档与
代码修改同时出现的任务，以及低置信度 OOD abstain。它们说明单次任务级 Policy
对复杂任务分解仍有限。下一步优先改进任务表示和候选动作，而不是简单增加模型参数。

### Q40：项目中最难的部分是什么？

最难的不是微调模型，而是定义可信的 Outcome。路由没有唯一标签，Teacher 和
LLM Judge 又可能互相强化偏见。我花更多精力在固定 fixture、Verifier-first、候选
执行、失败分类和数据切分上。只有先保证“成功”和“成本”可比较，DPO 才有可靠信号。

### Q41：这个项目的核心创新点是什么？

它不是简单做模型选择分类，而是把 Agent、执行模式、初始工具和风险建议放进一个
受约束的联合动作空间，并用真实执行 Outcome 而不是静态 Teacher 标签训练。同时
安全权限留在确定性层，使学习策略只负责柔性权衡。这种分层让算法优化、成本控制和
生产安全能够在同一套评测里讨论。

### Q42：项目有哪些局限？

第一，Policy 只做任务级初始决策，不能逐步规划或动态重路由；第二，执行轨迹规模仍
较小，强 Agent 自身的随机性会给偏好标签带来噪声；第三，评测集中在 CoWiki 场景，
不能直接声称泛化到任意 Agent 和未知工具；第四，成本依赖价格快照，必须同时报告
token和墙钟时间。

### Q43：下一步怎么做？

先完成真实 CoWiki 只读预检索和可复位 fixture Worktree 执行，替换当前模拟执行器；
然后扩展到 60 条人工 canonical Seed，验证 Verifier 和轨迹采集稳定性，再生成完整
训练集。模型上线采用 Shadow 和 Assisted 两阶段，通过失败采集、人工复核、离线
重训和固定回归集形成数据闭环，而不是在线自动更新。
